# Repo ↔ Production drift report

**Date:** 2026-08-15
**Project:** Supabase `mynwfkgksqqwlqowlscj`
**Method:** every claim in `CODE_REVIEW.md` that touched the database was re-verified against the live schema before any fix was written.

---

## Why this document exists

Four of the eight "critical" findings in the audit were **already fixed in production** and only looked broken because the fix was applied out-of-band — via MCP or the SQL editor — and never written back into `supabase/migrations/`.

That is not a harmless bookkeeping gap. It cuts both ways:

- **A rebuild is less safe than production.** Anyone standing up a preview branch, a DR restore, or a second environment from this directory would get a database missing `security_invoker`, missing revoked `anon` grants, missing pinned `search_path`s, and with a `SET NULL` foreign key where production has `CASCADE`.
- **Real findings drown.** Half of my own critical list was noise generated by stale files. The one genuinely broken thing — `night_audit_log` — was harder to see because of it. A reviewer who trusted the repo would have spent their day on the wrong four.

The reconciliation migration (`20260815_audit_reconcile_repo_to_prod.sql`) closes the gap. This document records what the gap *was*.

## The one that was real

**`night_audit_log` had a policy without a grant.**

```
nal_tenant_update  →  FOR UPDATE TO crm_tenant  USING (tenant_id = current_tenant_id())   ✅ present
GRANT UPDATE ON night_audit_log TO crm_tenant                                              ❌ absent
```

A policy is not a permission. Postgres checks the table grant first, so `crm_tenant` received `42501: permission denied` on every drawer write from `app/api/crm/close-day/route.ts:74` — and because that call discarded its return value, the failure was invisible. Every closed day re-downloaded with `opening_token = 0, payouts = 0`, roughly a **৳17,000 error in the Closing Balance** on a typical day.

This is the same root cause as the documented 2026-07-04 incident (*"missing crm_tenant grant → night-shift payments leaked into the next business day"*). That one was worked around in `/api/crm/payment` and `/api/crm/reservation` with a service-role fallback; `close-day` and `restaurant` never got the workaround, and the underlying cause was never fixed.

**Fixed 2026-08-15.** Grant applied, `tenant_id` made `NOT NULL` with an FK, the `OR tenant_id IS NULL` policy arm removed, an INSERT policy added, and — so this cannot happen a third time — `ALTER DEFAULT PRIVILEGES` now covers every future table and sequence in `public`.

**Verified after the change:** 62 rows writable as `crm_tenant`; `lumeademo` still sees 0 of Hotel Fountain's rows.

## Why the drift happened

`GRANT ... ON ALL SEQUENCES IN SCHEMA public` and `GRANT ... ON <explicit list of 32 tables>` both expand **at execution time**. They are snapshots, not standing rules. Every table added after 2026-07-02 needed a manual grant, and the manual step is exactly the one that gets skipped under time pressure.

Combined with a workflow where urgent hardening goes in through the SQL editor (fast, correct, unversioned) rather than through a migration (slower, correct, versioned), drift was the expected outcome rather than an accident.

`ALTER DEFAULT PRIVILEGES` removes the recurring manual step. The conformance assertion at the end of the reconciliation migration removes the silence — it raises rather than degrading quietly:

```sql
-- fails the migration if any tenant-scoped table lacks RLS, a policy, or a crm_tenant grant
SELECT string_agg(c.relname, ', ') FROM pg_class c ...
 WHERE ... AND (NOT c.relrowsecurity
             OR NOT EXISTS (SELECT 1 FROM pg_policies p WHERE p.tablename = c.relname)
             OR NOT has_table_privilege('crm_tenant', c.oid, 'SELECT'));
```

Wire that same query into CI and the July and August incidents both become build failures instead of month-long silent money errors.

## Scope limit worth preserving

The reconciliation **deliberately does not touch** the `anon` EXECUTE grants on the host→tenant routing functions — `current_tenant_id`, `get_my_tenant_id`, `lumea_pre_request`, `current_staff_role`, `is_admin`. Those grants are intentional and required for host-routed RLS; revoking them breaks the Rooms matrix (recorded in project memory, 2026-06-19).

The Supabase security advisor still reports them as `0028`/`0029` WARNs. **That is expected and must not be "fixed."** After this migration those five are the *only* functions in that list — the 12 lead-pipeline RPCs are gone from it, which is the signal that the revoke landed.
